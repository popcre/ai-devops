THREE DISTINCT FAILURE MODES.

MODE 1 - FINDINGS DISCARDED ABOVE THE VERDICT HEADING (1 occurrence, the most dangerous).
Rotation sequence 202, PR #1233, head 6ff9272effb7f3f24a67a262cee0c666f33b6af8. Kimi completed successfully and returned a correct "VERDICT: REVISE" naming ONE blocking finding. The finding itself never reached the caller. All that survived was the summary sentence: "Finding 1 is a live, reachable path that re-creates the exact wedge defect the issue enumerates, through the very validation this PR adds, with zero test coverage." No file, no line, no predicate, no input value.

Reproduced THREE times:
  (a) ai-kimi new NAME --prompt-file BRIEF                      -> findings above the verdict cut
  (b) ai-kimi ask NAME "Restate ALL of your findings in full"   -> same
  (c) ai-kimi ask NAME with an explicit instruction to put every finding INSIDE one final block headed "## Findings" -> STILL cut, because Kimi then wrote "## Verdict" BELOW "## Findings" and the extractor cut at the later heading.

Diagnosis: the extractor keeps everything from the LAST heading onward and discards the rest. Nothing else persists it. ai-kimi show and ai-kimi transcript both failed from the review sandbox ("no session NAME for caller claude in this repository", plus "jq: error: Could not open file : Invalid argument"). The session JSON at ~/.local/state/ai-devops/kimi/sessions/4c4d070b02d7/claude--seq202-1219-nbcu-count-gate.json contains ONLY metadata - twelve keys (kimi_session_id, repo, repo_remote, review_workspace, review_kind, name, caller, mode, model, created, updated, turns) - with no message content at all.

WORKAROUND FOUND AND PROVEN, used in every brief afterwards: instruct the model that only the FINAL block is captured and that it must put findings AND the verdict together in ONE block beginning with the heading "## Verdict", writing no heading after it. Naming "## Verdict" specifically is what makes it work. This is a workaround, not a fix: it depends on the model obeying a formatting rule, and any reviewer that writes a heading after its findings still loses them.

MODE 3 - SIX-SECOND EXIT 127 DEATHS (9 occurrences, all after Mode 2).
Rotation sequences 216, 218, 220, 222, 224, 228, 230, 232, 234. Exit 127 is "command not found". Six seconds is far too fast for any real work. This looks like the wrapper failing to locate or launch its provider binary, or failing a credential/auth step, and surfacing it as a bare non-zero exit rather than a named error. THE CALLER CANNOT DISTINGUISH THIS FROM A MODEL THAT REVIEWED AND CRASHED. All nine came AFTER the usage-limit hit at 16:14, which suggests the wrapper never recovered from that state.

FOURTH, SEPARATE DEFECT AFFECTING BOTH WRAPPERS - FALSE ".ai/reviews is not git-ignored" WARNING.
Both ai-kimi and ai-grok-review printed, on essentially every run:
  warning: not writing a review file: '.ai/reviews' is not git-ignored in PATH (it would be committable). Add '.ai/reviews/' to .gitignore.
The warning is FALSE. Line 36 of C:/repos/shared-db/.gitignore is literally ".ai/reviews/", and git status --porcelain after a run is empty. The check is wrong, not the repository. Consequence: the wrapper silently skips writing the review file, which would otherwise have been the LAST SURVIVING COPY of the findings lost in Mode 1. The ignore test should use git check-ignore rather than whatever string comparison it currently performs.

OPERATIONAL IMPACT.
Each Kimi failure cost a full rotation cycle: detect no verdict, call --replace-failed-reviewer with a recognised failure code, rebuild the review sandbox, re-run on the replacement. Eleven times. With GLM and Qwen already paused by the owner, the rotation was effectively down to Grok alone for most of the session, which removes the independent second opinion the rotation exists to provide - and that mattered: on TWO occasions a second reviewer overturned the first reviewer's conclusion, and on one of those the second reviewer refuted an author's design rationale using the author's own test fixture.

Note also that --replace-failed-reviewer REFUSES when the pull request is a merged one ("REFUSED: review replacement requires the exact open PR head"), which is the case for every production-promotion review. So a Kimi assignment landing on a promotion cannot be repaired through the tool at all and has to be worked around by hand.
